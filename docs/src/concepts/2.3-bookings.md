# 2.3 Bookings in the database

Step 2.3 adds the `bookings` table to every tenant schema, in a second tenant migration,
`migrations/tenant/00002_bookings.sql`. Its main rule is an **exclusion constraint**: Postgres
itself refuses a booking that overlaps another one for the same space. That is the README's "no
overlapping bookings, and only one of two simultaneous requests wins", and from 2.5 the Postgres
store relies on it instead of checking first.

The table also stores who made a booking for a member (`booked_by`), the approval deadline and
when the member approved. Only cancelled rows are ignored by the constraint, so a pending booking
holds its slot.

There's little new Go in this step: it is SQL, a psql script, and integration tests in the style
of 2.2. The binary doesn't change; the store that uses this table arrives in 2.4 and 2.5.

```sh
make db-up migrate-platform                # as in 2.1
make test-integration
make migrate-tenant TENANT=tenant_23       # an existing tenant; new ones get 00002 already
docker compose exec -T db psql -U cowbook -d cowbook -v tenant=tenant_23 < examples/2.3-bookings.sql
```

Use your own tenant's schema name. The script books Room A for Ana from 10:00 to 11:00, then:

```
ERROR:  conflicting key value violates exclusion constraint "bookings_no_overlap"    -- Bo, 10:30-11:30
INSERT 0 1                                                                           -- Bo, 11:00-12:00
INSERT 0 1                                                                           -- staff book 15:00 for Ana
ERROR:  conflicting key value violates exclusion constraint "bookings_no_overlap"    -- Bo, 15:30: pending holds it
UPDATE 1                                                                             -- Ana cancels 10:00
INSERT 0 1                                                                           -- Bo, 10:00-10:45, now free
ERROR:  new row for relation "bookings" violates check constraint "bookings_starts_before_ends"
ERROR:  new row for relation "bookings" violates check constraint "bookings_approved_needs_deadline"
ERROR:  update or delete on table "members" violates foreign key constraint "bookings_member_id_fkey" on table "bookings"
```

It ends by listing the four bookings, Ana's cancelled one included, and rolls everything back.

The table is in the [Database reference](../reference/database.md#bookings).

## A new migration, not an edited one

`00001_tenant.sql` is committed and every existing tenant has run it. goose records version 1 in
each schema's `goose_db_version` and never runs it again, so a table added to that file would
never reach them. Changes go in a new, higher version. Editing an applied migration also makes
the file lie: it no longer describes what the databases ran.

New tenants run both versions in `CreateTenant`. Existing ones need `make migrate-tenant`, which
runs goose with the tenant's schema on the `search_path`. It passes `search_path` as a URL
parameter: pgx sends parameters it doesn't know to Postgres as settings for the connection, the
same thing `Provisioner.migrate` does with `RuntimeParams`. Migrating every tenant at once is 5.5.

## Exclusion constraints

A unique constraint says no two rows have equal values. An exclusion constraint generalizes it: no
two rows have values for which *all* the listed operators are true.

```sql
CONSTRAINT bookings_no_overlap EXCLUDE USING gist (
    space_id WITH =,
    tstzrange(starts_at, ends_at) WITH &&
) WHERE (cancelled_at IS NULL)
```

reads "no two rows where `space_id = space_id` and the ranges overlap (`&&`)". Two bookings of
different spaces pass, two bookings of one space at different times pass.

Like a unique constraint, it is backed by an index, and the index is what makes it safe under
concurrency. When two transactions insert overlapping bookings at the same moment, the second one
waits on the first; if the first commits, the second fails. No read-then-write window exists for a
bug to slip into, which is what 1.5's [read, check, write](1.5-services-and-stores.md#read-check-write)
needed a store to guarantee.

The failure has SQLSTATE `23P01`, `exclusion_violation`. The test checks the code as well as the
constraint name, since 2.5 maps that code to `ErrSlotTaken`.

## GiST and `btree_gist`

A B-tree index, the default, can only answer "equal" and "less than". Overlap isn't either, so
the constraint uses a **GiST** index, which can index ranges and answer `&&`. GiST doesn't know
`=` on a plain `bigint`, though. The `btree_gist` extension teaches it, which is why 2.1 created
it in the `shared` schema.

The migration runs with `shared` on the `search_path`, so Postgres finds the operator class when
it creates the index. The index stores which one it uses, so later queries don't need `shared` on
their path to keep the constraint working.

## Ranges and half-open bounds

`tstzrange(starts_at, ends_at)` builds a range of `timestamptz` values. With two arguments the
bounds are `[)`: the start is included, the end is not. A booking from 10:00 to 11:00 and one from
11:00 to 12:00 don't overlap, which matches `Booking.End`, documented as not included.

The range is built in the constraint rather than stored, so the table keeps two plain columns that
map to two `time.Time` values. Both are `timestamptz`, an instant: comparing them doesn't depend on
the timezone they were written in. The test "same slot in another timezone" writes 11:00+01, the
same instant as 10:00Z, and is refused.

## A partial constraint, and why `now()` can't be in it

`WHERE (cancelled_at IS NULL)` limits the constraint to rows not cancelled, the same idea as 2.2's
[partial unique index](2.2-tenant-schemas.md#the-tenant-tables). Cancelling sets `cancelled_at`,
and the slot is free in the same statement.

It would be nice to also ignore pending bookings past their deadline, but
`WHERE approval_deadline > now()` isn't allowed: a constraint's condition has to give the same
answer for a row forever, and `now()` changes. A row that passed yesterday would silently stop
being checked today. So a lapsed pending booking keeps its slot until something cancels it. The
decision was lazy expiry: 2.5's `CreateBooking` first cancels lapsed pending bookings that overlap
the new one, in the same transaction. The test "overlapping a lapsed pending booking" pins today's
behavior.

## Rules the database checks, and rules it leaves to Go

Check constraints see one row at a time. So the table checks what one row can show:

- `bookings_starts_before_ends`: a booking has a length.
- `bookings_attendees_positive`: someone attends.
- `bookings_approval_iff_staff`: `booked_by` and `approval_deadline` are both set or both `NULL`.
  Every staff booking needs approval, and only staff bookings do.
- `bookings_approved_needs_deadline`: only a booking that needed approval can be approved.

Capacity, maximum length, opening hours, the space being available and the start not being in
the past all need the space's row, its location's timezone, or the clock. They stay in
`cowbook.NewBooking`, which every booking goes through.

The foreign keys have no `ON DELETE CASCADE`. A booking is history, so deleting a space or member
that has bookings is refused. Members are soft-deleted anyway.

## `NULL` and Go's zero time

`booked_by`, `approval_deadline`, `approved_at` and `cancelled_at` are `NULL` until they mean
something, where `Booking` uses `0` and a zero `time.Time`. Not storing Go's zero time
(`0001-01-01`) keeps the rows honest for anyone reading them in psql, and keeps `IS NULL` working
in constraints like the one above. The store converts one to the other in 2.4 and 2.5.

## `make migrate-check` moves to its own database

Until now `migrate-check` ran up, reset, up against the dev database. Once a tenant has a
`bookings` table, its constraint depends on `btree_gist`, and the platform migration's Down can't
drop the extension: Postgres refuses (SQLSTATE `2BP01`) rather than break the constraint. Before
that, the same reset would have dropped `platform.tenants`, rows and all. The target now creates
a throwaway `cowbook_migrate_check` database, checks the platform migrations there and drops it.
The `database` URL parameter picks the database, as `search_path` does for `migrate-tenant`.

## Known gaps

- `booked_by` has no foreign key: staff accounts arrive in M4, which adds it.
- A lapsed pending booking blocks its slot until lazy expiry (2.5) cancels it.
- Existing tenants only get new versions through `make migrate-tenant`, one at a time (5.5).
- Concurrent inserts are proven in 2.5, through the store with many goroutines. This step's tests
  insert one row at a time.
