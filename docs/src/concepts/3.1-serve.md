# 3.1 `cowbook serve`

Step 3.1 starts M3. The binary gets its third subcommand, the HTTP server that every later step
adds routes to:

- **`cowbook serve`** listens on `COWBOOK_ADDR` (default `localhost:8080`) until Ctrl-C or
  SIGTERM, then shuts down gracefully: requests in flight get their answer first.
- **`GET /healthz`** pings Postgres: `200 {"status":"ok"}`, or `503 {"status":"unavailable"}`
  with the reason in the log only.
- **Config from the environment**: `DATABASE_URL` (required), `COWBOOK_ADDR` and
  `COWBOOK_LOG_LEVEL`. `cowbook serve -h` lists them.
- **Logs through `log/slog`**, as text on stderr.
- **Two new packages**: `internal/httpapi` holds the routes, `internal/server` runs a handler
  until a context ends. `cmd/cowbook/serve.go` wires them to the pool.

Run it against the compose database:

```sh
just db-up migrate-platform        # as in 2.1
just serve                         # go run ./cmd/cowbook serve, with .env loaded
```

In a second terminal:

```sh
curl -i localhost:8080/healthz             # 200 {"status":"ok"}
curl -i -X POST localhost:8080/healthz     # 405 Method Not Allowed
curl -i localhost:8080/nope                # 404 Not Found
docker compose pause db                    # the database stops answering
curl -i localhost:8080/healthz             # after 2s: 503 {"status":"unavailable"}
docker compose unpause db
```

Then Ctrl-C in the first one. The log:

```text
level=INFO msg=listening addr=127.0.0.1:8080
level=WARN msg="health check failed" err="context deadline exceeded"
level=INFO msg="shutting down" timeout=10s
level=INFO msg=stopped
```

## `http.Server` and its timeouts

`http.ListenAndServe(addr, h)` is the one-line server in every tutorial. It builds an
`http.Server` with every field at its zero value, and for the timeouts zero means **none**. A
client that sends its headers one byte a minute (an attack called slowloris), or never reads the
answer, then holds a connection and a goroutine for as long as it likes. `server.New` builds the
struct itself:

```go
return &http.Server{
	Handler:           h,
	ReadHeaderTimeout: readHeaderTimeout, // 5s: request line and headers
	ReadTimeout:       readTimeout,       // 15s: the whole request, body included
	WriteTimeout:      writeTimeout,      // 15s: from the end of the headers to the end of the answer
	IdleTimeout:       idleTimeout,       // 60s: a kept-alive connection between requests
	ErrorLog:          slog.NewLogLogger(log.Handler(), slog.LevelError),
}
```

- **`WriteTimeout` must outlast the slowest handler.** The health check gives up after 2 s, well
  inside 15 s. A handler that runs longer than `WriteTimeout` finishes its work, but the client
  gets a closed connection instead of the answer.
- **`ErrorLog`** is where the server reports its own trouble, such as a panic in a handler or a
  bad TLS handshake. It takes the old `*log.Logger`; `slog.NewLogLogger` makes one that writes
  through our `slog` handler, so those lines look like all the others.

## Routes with methods in `http.ServeMux`

Since Go 1.22 a `ServeMux` pattern can name a method:

```go
mux := http.NewServeMux()
mux.Handle("GET /healthz", healthz(db, log))
```

The mux then does three things for free: `GET` (and `HEAD`, which a `GET` route also answers)
reaches the handler, any other method gets `405 Method Not Allowed` with an `Allow` header, and
any other path gets `404`. Before 1.22 each handler had to check `r.Method` itself. 3.3 replaces
the mux with chi, which also groups routes under `/api/o/{slug}` and runs middleware.

## The health check

```go
func healthz(db Pinger, log *slog.Logger) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		ctx, cancel := context.WithTimeout(r.Context(), pingTimeout)
		defer cancel()

		w.Header().Set("Content-Type", "application/json")
		if err := db.Ping(ctx); err != nil {
			log.Warn("health check failed", "err", err)
			w.WriteHeader(http.StatusServiceUnavailable)
			io.WriteString(w, `{"status":"unavailable"}`+"\n")
			return
		}
		io.WriteString(w, `{"status":"ok"}`+"\n")
	})
}
```

- **A function that returns a handler.** `healthz` takes what the handler needs and returns a
  closure over it, the same shape as [`WithTenant`'s closure](2.4-sqlc-and-withtenant.md#closures-for-transaction-scope)
  turned around. `http.HandlerFunc` is a function type with a `ServeHTTP` method, so a plain
  function becomes an `http.Handler` by conversion.
- **`r.Context()` is the request's context.** It ends when the client disconnects or the server
  is closed. `context.WithTimeout` derives a child that also ends after 2 s, so a database that
  accepts the connection and then hangs gives a 503 instead of a request that never finishes.
  `defer cancel()` releases the timer as soon as the handler returns.
- **Headers before the status, the status before the body.** `Header().Set` only counts until
  the first `WriteHeader` or `Write`. A `Write` without `WriteHeader` sends `200`.
- **The reason stays in the log.** `/healthz` needs no login, and a pgx connection error names
  hosts and ports. The client learns only that it's unavailable.
- **`Pinger` is defined where it's used.** `httpapi` declares the one method it needs, and
  `*pgxpool.Pool` meets it without knowing, as `repl.Store` does in
  [2.7](2.7-repl-on-postgres.md#interfaces-defined-by-the-consumer). The tests pass a fake that
  fails on demand, and remembers whether its context had a deadline.

The decision to ping the database, rather than answer `200` whenever the process runs, makes the
check mean "this server can do its work". Kubernetes-style setups split the two into a liveness
and a readiness check; one is enough to run locally.

## Structured logs with `log/slog`

`log/slog` (Go 1.21) logs a message plus key-value pairs, which a handler formats:

```go
log := slog.New(slog.NewTextHandler(os.Stderr, &slog.HandlerOptions{Level: cfg.LogLevel}))
log.Info("listening", "addr", ln.Addr().String())
// time=... level=INFO msg=listening addr=127.0.0.1:8080
```

- **Handler vs logger.** The `Logger` is what code calls; the `Handler` decides the format and
  the destination. `slog.NewJSONHandler` would print one JSON object per line from the same
  calls. `slog.DiscardHandler` (Go 1.24) drops everything, for tests that don't read the log.
- **Levels.** `Debug`, `Info`, `Warn` and `Error`; `HandlerOptions.Level` drops anything below
  the one set. `slog.Level` parses its own names (`UnmarshalText`, any case), which is how
  `COWBOOK_LOG_LEVEL` is read.
- **A logger is passed in, not global.** `slog.Default()` exists, but passing `*slog.Logger` to
  `httpapi.NewHandler` and `server.Run` lets a test hand in one that writes to a
  `bytes.Buffer` and check what was logged.
- **stderr.** Logs are diagnostics; stdout stays free for a command's actual output, as in the
  REPL.

## Config from the environment

```go
func loadServeConfig(getenv func(string) string) (serveConfig, error)
```

The binary calls `loadServeConfig(os.Getenv)`; the test passes a function that reads a map.
That is the [injected clock](1.5-services-and-stores.md#dependency-injection-including-the-clock)
again: a function value standing in for something global, so each test sees exactly the
variables it names and never the developer's real environment. `t.Setenv` would also work, but
it changes the whole process, so the test couldn't run in parallel.

`COWBOOK_ADDR` defaults to `localhost:8080`, not `:8080`. `:8080` listens on every network
interface, and nothing here is fit for a network yet: there's no login until M4, and the app
connects as the database superuser until 5.1.

`just serve` gets the variables from `.env`, which the justfile includes and exports; the new
ones are in `.env.example`.

## Listening on port 0

`runServe` opens the listener itself and hands it to `server.Run`, instead of giving the server
an address:

```go
ln, err := net.Listen("tcp", cfg.Addr)
...
log.Info("listening", "addr", ln.Addr().String())
```

- **Port 0 asks the OS for a free port.** `ln.Addr()` tells which one it gave. The server tests
  listen on `127.0.0.1:0`, so they never collide with each other or with a `cowbook serve`
  you have running, and `COWBOOK_ADDR=localhost:0` works too.
- **A taken port fails before anything is served,** with a plain error and exit code 1:
  `listen tcp 127.0.0.1:8080: bind: address already in use`.

## Graceful shutdown

`server.Run` is the heart of the step:

```go
served := make(chan error, 1)
go func() { served <- srv.Serve(ln) }()

select {
case err := <-served:
	return fmt.Errorf("serve: %w", err)
case <-ctx.Done():
}

shutdownCtx, cancel := context.WithTimeout(context.WithoutCancel(ctx), shutdownTimeout)
defer cancel()
if err := srv.Shutdown(shutdownCtx); err != nil {
	return fmt.Errorf("shutdown: %w", err)
}
if err := <-served; !errors.Is(err, http.ErrServerClosed) {
	return fmt.Errorf("serve: %w", err)
}
return nil
```

- **`Serve` blocks**, so it runs in a goroutine and reports through a channel. The buffer of 1
  lets that goroutine send and end even when nobody is receiving yet.
- **`select` waits for whichever comes first**: `Serve` failing, or `ctx` ending. `Serve` never
  returns `nil`; before a shutdown, anything it returns is a real failure.
- **`Shutdown` vs `Close`.** `Shutdown` closes the listener, so no new connection is accepted,
  closes idle connections, and **waits** for active ones to finish their request. `Close` drops
  everything at once. `Shutdown` returns early with the context's error if the deadline passes
  first; the requests still running then die with the process.
- **`context.WithoutCancel(ctx)`.** `ctx` is already cancelled, so a deadline derived from it
  would be over before it began. `WithoutCancel` keeps its values and drops its cancellation, as
  `WithTenant` does for its rollback ([2.4](2.4-sqlc-and-withtenant.md)).
- **`http.ErrServerClosed`** is what `Serve` returns once `Shutdown` has run: the normal end,
  not an error.

### Signals: `signal.NotifyContext`

```go
ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
defer stop()
context.AfterFunc(ctx, stop)
```

- **`NotifyContext`** returns a context that ends on the first SIGINT (Ctrl-C) or SIGTERM (what
  `kill`, Docker and systemd send). From then on those signals no longer kill the process; they
  cancel `ctx`, which `server.Run` is waiting on.
- **A second Ctrl-C.** Without more code, every later Ctrl-C would cancel an already cancelled
  context, and a stuck shutdown could only be ended with `kill -9`. `context.AfterFunc(ctx, stop)`
  (Go 1.21) runs `stop` in its own goroutine once `ctx` ends. `stop` hands the signals back to
  Go's default handling, so the second Ctrl-C kills the process at once (exit status 130).
- **What "default" means.** `stop` gives back the handling the process **started with**. A shell
  script that runs `cowbook serve &` without job control starts it with SIGINT *ignored* (check
  the `SigIgn` line in `/proc/<pid>/status` of any `sleep 9 &`: `0x6` is SIGINT and SIGQUIT).
  `signal.Notify` turns SIGINT on anyway, and after `stop` it is ignored again. So in a script,
  `kill -INT` twice only shuts down gracefully; `kill -TERM` twice kills (status 143). In a
  terminal, where Ctrl-C was never ignored, the second one kills. Found while checking this step
  by hand; `env --default-signal=INT cowbook serve &` gives a script the terminal's behavior.

### Shutting down in order

```go
pool, err := postgres.NewPool(ctx, cfg.DatabaseURL)
...
defer pool.Close()
...
if err := server.Run(ctx, srv, ln, log, shutdownTimeout); err != nil {
```

`server.Run` only returns after the requests have finished or the timeout has passed, and
`pool.Close` is deferred, so it runs after that. The pool closes once no handler can use it. The
other order would make the last requests fail with a closed pool.

The pool also connects lazily: `NewPool` doesn't open a connection. `runServe` pings once
before it listens, so a wrong `DATABASE_URL` or a stopped database stops `serve` at startup
(exit 1) rather than surfacing as 503s afterwards.

## Exit codes

| Exit code | Means |
| --- | --- |
| `0` | Stopped by a signal after a clean shutdown, or `-h` |
| `1` | `DATABASE_URL` unset, a bad `COWBOOK_LOG_LEVEL`, Postgres unreachable at startup, the address taken, or requests still running after the 10 s shutdown timeout |
| `2` | A stray argument: `serve` takes none yet |
| `130`, `143` | Killed by a second SIGINT or SIGTERM during the shutdown |

`serve` parses an empty `flag.NewFlagSet("serve", ...)` with its own `Usage`, so `-h` and a
stray argument behave as they do for `repl`. 3.2 moves all subcommands to `flag`.

## Testing a server: `httptest` and a real listener

Two kinds of test, for two kinds of code:

- **A handler is a function of a request.** `httptest.NewRequest` builds one without a network,
  `httptest.NewRecorder` is an `http.ResponseWriter` that keeps the status, headers and body,
  and `h.ServeHTTP(rec, req)` runs it. `internal/httpapi`'s tests are plain function calls.
- **Shutdown is about connections and time,** so `internal/server`'s tests run the real thing:
  `server.Run` on a port-0 listener in a goroutine, a real `http.Get`, and a handler that blocks
  on a channel until the test releases it. Cancelling the context plays the part of Ctrl-C.

The graceful test checks the order of events: the handler is entered, the context is cancelled,
`Run` has **not** returned 100 ms later, the handler is released, the client gets its `200`, and
only then `Run` returns `nil`. Replacing `srv.Shutdown(...)` with `srv.Close()` makes it and the
timeout test fail, which shows they test the shutdown and not just a server that stops
([proving a test can fail](2.6-cancel-and-delete.md#proving-the-tests-can-fail)).

## What the tests cover

- `internal/httpapi`: `TestHealthzOK` (status, body, content type, a ping with a deadline),
  `TestHealthzDatabaseDown` (503, no error text in the body, a `WARN` line with it in the log),
  `TestHealthzMethods` (GET and HEAD 200, POST and DELETE 405) and `TestUnknownPath` (404).
- `internal/server`: `TestRunFinishesRequestsInFlight`, `TestRunShutdownTimeout` (an error
  wrapping `context.DeadlineExceeded`), `TestRunServeFails` (a closed listener returns at once)
  and `TestNewSetsTimeouts`. All under `-race`.
- `cmd/cowbook`: `TestLoadServeConfig`, a table of defaults, all variables set, a level in
  capitals, no `DATABASE_URL` and an unknown level.
- By hand, with the commands at the top: the 200, 405, 404 and 503 answers, a request drained
  during shutdown, and the exit codes in the table.

## Known gaps

- **No request log.** Only startup, shutdown and failed health checks are logged. A
  request-logging middleware belongs with 3.3, where middleware arrives.
- **`/healthz` costs a database round trip per call**, and anyone who can reach the port can
  call it. Fine on `localhost`; rate limits arrive in 5.4.
- **No integration test for `runServe` itself.** Its parts are tested, and the wiring is checked
  by hand. 3.3's first tenant route will bring an end-to-end test through a real server.
