# 2.7 The REPL on Postgres

Step 2.7 finishes M2. Spaces, members and bookings are all in Postgres, and `cowbook repl` can
use them:

- **`cowbook repl -store=postgres -tenant=<slug>`** runs the REPL over one tenant's schema in
  `DATABASE_URL`, so what you add survives a restart. `-store=memory` is still the default.
- **The session takes `repl.Store`**, a small interface the `repl` package defines for itself,
  instead of `*memstore.Store`. Both stores meet it.
- **`postgres.MemberStore`** gets `CreateMember` and `ListMembers`, **`postgres.BookingStore`**
  gets `ListBookings`, and **`postgres.SpaceStore`** gets `LocationFor`.
- **`postgres.Stores`** puts one tenant's three stores in one value by embedding them.
- **`postgres.LookupTenant`** turns a slug into a tenant id and refuses tenants that aren't
  active.
- **`cowbook.ErrEmailTaken`**: a member who isn't deleted already has that email. Both stores
  return it.
- **IDs come from the store.** The REPL no longer numbers spaces and members itself.

Run it against the compose database:

```sh
make db-up migrate-platform                       # as in 2.1
go run ./cmd/cowbook create-tenant north-hub "North Hub"
go run ./cmd/cowbook repl -store=postgres -tenant=north-hub
```

```text
[nobody]> space add Desk hot_desk 1 8h
ok space #1
[nobody]> space add Sala meeting_room 4 2h mon-fri/09:00-18:00 Europe/Madrid
ok space #2
[nobody]> member add Ana ana@x.com
ok member #1
[nobody]> as member 1
ok acting as member 1
[member 1]> book 1 2026-11-17 09:00-10:00
ok booking #1: space 1, Tue 2026-11-17 09:00-10:00 UTC
[member 1]> quit
```

Start it again with the same flags, and `space list`, `member list` and `booking list` show it
all. `member add Ana2 ANA@x.com` now says `error: email is already taken by another member`.

## Interfaces defined by the consumer

Up to 2.6, the session held a `*memstore.Store`, a concrete type from another package. Running
it on Postgres needs something both stores can be. In Go, the package that **uses** a behavior
declares the interface for it, and keeps it as small as its own needs:

```go
// in internal/repl
type Store interface {
	LocationFor(ctx context.Context, tz *time.Location) (int64, error)
	CreateSpace(ctx context.Context, sp cowbook.Space) (cowbook.Space, error)
	GetSpace(ctx context.Context, id int64) (cowbook.Space, *time.Location, error)
	ListSpaces(ctx context.Context) ([]cowbook.Space, error)
	CreateMember(ctx context.Context, m cowbook.Member) (cowbook.Member, error)
	ListMembers(ctx context.Context) ([]cowbook.Member, error)
	ListBookings(ctx context.Context) ([]cowbook.Booking, error)
}
```

These are the seven calls the REPL's commands make themselves. Everything that changes a booking
or deletes a member still goes through the services. Neither `memstore` nor `postgres` imports
`repl` or mentions `repl.Store`. Interfaces are satisfied implicitly
([1.5](1.5-services-and-stores.md#implicit-interfaces)), so a type with these methods is a
`repl.Store` without saying so.

This is the same move `cowbook` made in 1.5 with `BookingStore`, `SpaceStore` and `MemberStore`:
the services declare what they need, and the stores implement it. It follows from the Go
proverb "accept interfaces, return structs". `memstore.New` and `postgres.NewStores` return
concrete types with all their methods. Each caller then takes only the part it uses.

The opposite, an interface declared next to its implementation for everyone to use, tends to grow
into the union of every caller's needs. `repl.Store` has list methods no service needs, and the
`cowbook` interfaces have `SaveDeletion`, which the REPL never calls. Keeping them apart keeps
the list methods off the domain's interfaces, as decided in
[1.10](1.10-repl-catches-up.md#list-methods-stay-off-the-interfaces).

### Interfaces made of interfaces

`main` needs one value it can pass as all four: `repl.Store` for the session, and the three
`cowbook` interfaces for the services. An interface can embed other interfaces:

```go
type replStore interface {
	repl.Store
	cowbook.BookingStore
	cowbook.SpaceStore
	cowbook.MemberStore
}
```

`GetSpace` is in both `repl.Store` and `cowbook.SpaceStore`. That is allowed since Go 1.14,
because the two signatures are identical. If they differed, this wouldn't compile.

## Struct embedding: three stores as one value

`memstore.Store` is one type with every method. In Postgres, `SpaceStore`, `MemberStore` and
`BookingStore` are three types. `postgres.Stores` makes one value of them:

```go
type Stores struct {
	*SpaceStore
	*MemberStore
	*BookingStore
}
```

Each field has a type and no name, so it is **embedded**, as `SpaceParams` is in `SpaceRecord`
([2.4b](2.4b-space-store.md#embedded-structs)). This time what gets promoted is methods, not
fields. `stores.CreateMember(ctx, m)` means `stores.MemberStore.CreateMember(ctx, m)`. So
`Stores` has the methods of all three and meets every interface they meet between them,
`repl.Store` included, though `postgres` never sees that interface. The compile-time checks in
`internal/postgres/stores.go` show it:

```go
var (
	_ cowbook.BookingStore = Stores{}
	_ cowbook.SpaceStore   = Stores{}
	_ cowbook.MemberStore  = Stores{}
)
```

Two catches:

- **Name clashes.** If two embedded types had a method with the same name at the same depth,
  neither would be promoted, and calling it would be a compile error ("ambiguous selector"). The
  three stores have no shared names, so nothing is lost.
- **Not inheritance.** The promoted method still runs on the embedded store, with that store as
  its receiver. `Stores` adds nothing and overrides nothing. A method declared on `Stores` itself
  with a promoted method's name would hide the promoted one.

`Stores` is a value type holding three pointers, so copying it is cheap and the copies share the
stores. Like each store, it holds no connection.

## One location per timezone

Here the two stores disagreed. memstore kept a timezone on each space, and every space was at
location 1. Postgres keeps the timezone on `locations`, and `spaces.location_id` must point at a
real row. Location management is 3.7's job, so for now both stores get one more method:

```go
LocationFor(ctx context.Context, tz *time.Location) (int64, error)
```

It returns the location with that timezone, adding one named after the zone if there is none.
`space add` calls it before `NewSpace`. The syntax hasn't changed, but the timezone now picks the
location: UTC spaces share one, and the first space in `Europe/Madrid` gets another. Front desk
locations mean something now. `as frontdesk 7 2` can book the Madrid space and is refused at
the UTC ones (`TestSpaceTimezonePicksLocation`).

Zones compare by name (`tz.String()`), because two `time.LoadLocation("Europe/Madrid")` calls
return different pointers.

In Postgres the find and the insert run in one `WithTenant` transaction. Two sessions adding the
same new zone at once could both insert a row. Nothing refuses that, since two real locations
can share a zone, and `GetLocationByTimezone` takes the lowest id, so the later sessions
converge. 3.7 replaces this method with real locations.

## Creating members, and a taken email

`CreateMember` inserts the row with the domain's timestamps, as `CreateSpace` does
(2.4b). The partial unique index `members_email_key`
from [2.2](2.2-tenant-schemas.md#the-tenant-tables) refuses an email that a member who isn't
deleted already has. The store maps that `23505` to `cowbook.ErrEmailTaken`, with the same
`errors.As` check as for foreign keys
([2.4b](2.4b-space-store.md#foreign-key-errors)):

```go
var pgErr *pgconn.PgError
if errors.As(err, &pgErr) && pgErr.Code == "23505" && pgErr.ConstraintName == "members_email_key" {
	return cowbook.Member{}, cowbook.ErrEmailTaken
}
```

For a unique index, `ConstraintName` is the index's name. The index decides, not a read first,
so two sign-ups with one email can't both pass. memstore checks the same thing under its mutex.

`NewMember` lowercases the email, so `ANA@x.com` and `ana@x.com` collide in both stores.

## Picking a tenant

`LookupTenant(ctx, pool, slug)` reads `id` and `status` from `platform.tenants`:

| Row | Result |
| --- | --- |
| None | `ErrTenantNotFound`, wrapped with the slug |
| `active` | The id |
| `provisioning` or `suspended` | An error naming the status |

A `provisioning` tenant may not have its schema yet, and suspension (5.4) must block every route,
so only `active` tenants open. `ErrTenantNotFound` lives in `postgres`, not `cowbook`: there is
no `Tenant` domain type yet, and only the delivery layer turns a slug into an id.

## Flags for one subcommand: `flag.NewFlagSet`

`cowbook` still dispatches on `os.Args[1]` with a `switch`. 3.2 moves every subcommand to `flag`;
`repl` moves now, because it is the first to take options:

```go
fs := flag.NewFlagSet("repl", flag.ContinueOnError)
storeName := fs.String("store", "memory", "where data lives: memory, gone when the REPL ends, or postgres")
tenant := fs.String("tenant", "", "the operator's slug, with -store=postgres")
if err := fs.Parse(args); errors.Is(err, flag.ErrHelp) {
	return nil
} else if err != nil {
	return errUsage
}
```

- **A `FlagSet` per subcommand.** The package-level `flag.String` and `flag.Parse` use one global
  set for the whole program. A `FlagSet` gives `repl` its own flags, parsed from `os.Args[2:]`,
  so `create-tenant` will be able to have different ones.
- **`fs.String` returns a `*string`.** The flag's value lands there during `Parse`, so read
  `*storeName` after `Parse`, not before.
- **`ContinueOnError`.** On a bad flag, `Parse` prints the problem and the usage to stderr and
  returns an error. `ExitOnError` would call `os.Exit` itself, from inside a function, which
  makes it hard to test and skips `defer`s. Here `main` decides the exit code: `errUsage` gives 2.
- **`-h` is not an error.** `Parse` returns `flag.ErrHelp` after printing the flags, and the REPL
  exits 0.
- **Checks `flag` can't make.** `-store=postgres` without `-tenant`, `-tenant` with the memory
  store, an unknown store name, or a leftover argument all print a line and the usage, through
  `usageError`, and exit 2.

| Exit code | Means |
| --- | --- |
| `0` | The session ended, or `-h` |
| `1` | `DATABASE_URL` unset, Postgres unreachable, tenant unknown or not active, or reading stdin failed |
| `2` | A bad flag or argument |

## The clock stays fixed

The REPL clock still starts at Monday 16 November 2026, 08:00 UTC, in both modes, so a session
prints the same every run. With Postgres, that has a cost. The data stays, but the clock goes
back to its start on every run. A booking made after `clock add 48h` is in the future again
after a restart, and one made for 16 November may already be in the past when the next run
moves the clock on. Use `clock set` to go back to where you were. Starting from the wall clock
was the alternative, rejected so the two modes behave the same.

## What the tests cover

- `internal/memstore`: `TestLocationFor`, `TestCreateSpace` (IDs, timezone from the location,
  unknown location) and `TestCreateMember` (taken email, a deleted member's email reused).
  `newStore` now builds through these methods, so its spaces are 1 and 2 rather than 7 and 8.
- `internal/postgres`: `TestSpaceStoreLocationFor`, `TestMemberStoreCreateAndList`,
  `TestBookingStoreList` and `TestLookupTenant`, against the compose database.
- `internal/repl`: `TestSpaceTimezonePicksLocation`, a taken email in `TestMemberAdd`, and
  `TestSessionOverPostgresKeepsData`. That test runs a script on a new tenant, then a **second**
  session over the same tenant, which lists exactly what the first one stored. That is the
  restart, without a process.

## Known gaps

- `LocationFor` exists for the REPL only. 3.7 replaces it with location management.
- `space add` gets the location before `NewSpace` checks the rest, because `NewSpace` needs its
  ID. So a `space add` refused for, say, its kind can still leave a new location with no spaces
  in a new zone. Harmless, and gone with 3.7.
- The fixed clock and lasting data disagree after a restart, as described above.
- The REPL still has no `-server` mode. 3.3 adds a `Backend` interface with an HTTP
  implementation, which will grow out of `repl.Store`.
- The integration tests in `internal/repl` repeat the small create and drop tenant helper from
  `internal/postgres`, because test files can't be imported from another package.
