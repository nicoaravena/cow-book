# 2.1 Postgres and migrations

Step 2.1 gives the project a database: a local Postgres started with `compose.yaml`, goose to
apply migrations, and the first **platform** migration. It creates the `platform` schema with the
`tenants` table, and the `shared` schema with the `btree_gist` extension that 2.3's exclusion
constraint needs. No Go code changes yet. The runnable result is a SQL script for `psql`.

```sh
cp .env.example .env        # then set POSTGRES_PASSWORD, and the same password in DATABASE_URL
just db-up                  # start Postgres and wait until it is healthy
just migrate-platform       # apply migrations/platform, then print their status
docker compose exec -T db psql -U cowbook -d cowbook < examples/2.1-tenants.sql
just migrate-check          # up, all the way down, up again
just db-down                # stop it; the data stays in the pgdata volume
```

`psql` runs inside the container, so the host needs no Postgres client. `just db-psql` opens an
interactive prompt the same way.

The script inserts one good tenant, then tries five bad ones:

```text
INSERT INTO platform.tenants (slug, name) VALUES ('north-hub', 'North Hub')
RETURNING id, slug, name, status;
 id |   slug    |   name    |    status
----+-----------+-----------+--------------
  1 | north-hub | North Hub | provisioning
(1 row)

INSERT INTO platform.tenants (slug, name) VALUES ('north-hub', 'Another North Hub');
ERROR:  duplicate key value violates unique constraint "tenants_slug_key"
INSERT INTO platform.tenants (slug, name) VALUES ('Bad Slug', 'Bad Slug');
ERROR:  new row for relation "tenants" violates check constraint "tenants_slug_format"
...
INSERT INTO platform.tenants (id, slug, name) VALUES (99, 'west-hub', 'West Hub');
ERROR:  cannot insert a non-DEFAULT value into column "id"
```

It ends by listing the schemas (`platform`, `public`, `shared`) and showing `btree_gist` installed
in `shared`. The whole script runs in a transaction that it rolls back, so you can run it again.

The table and the Make targets are in the [Database reference](../reference/database.md).

## `go tool` again

0.1 added `staticcheck` as a tool. goose joins it:

```sh
go get -tool github.com/pressly/goose/v3/cmd/goose@v3.29.0
```

```text
tool (
	github.com/pressly/goose/v3/cmd/goose
	honnef.co/go/tools/cmd/staticcheck
)
```

`go tool goose` builds and runs exactly that version, with no global install. The cost shows in
`go.mod`: goose's command imports a driver for every database it supports (MySQL, SQLite,
ClickHouse, SQL Server and more), and `go.mod` lists everything a tool needs, so it grew from 14
lines to 84. None of it ends up in `cowbook`'s binary: tool dependencies are only built when you
run the tool. 3.2's `cowbook migrate` uses goose as a library with only the pgx driver.

v3.29.0 rather than the newest v3.30.1: a release younger than two weeks hasn't had time for
anyone to find a broken or malicious version.

## Compose

`compose.yaml` describes containers; `docker compose up` starts them.

```yaml
services:
  db:
    image: postgres:18
    environment:
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:?set POSTGRES_PASSWORD in .env}
    ports:
      - "${POSTGRES_PORT:-5432}:5432"
    volumes:
      - pgdata:/var/lib/postgresql
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U cowbook -d cowbook"]
```

- **`${VAR:?message}`** fails at once if the variable is unset or empty, rather than starting a
  database with no password. **`${VAR:-default}`** falls back to a default. Compose reads `.env`
  from the project directory by itself.
- **The volume** keeps the data when the container is removed. `just db-down` keeps it;
  `docker compose down -v` deletes it. The image only reads `POSTGRES_PASSWORD` when it creates a
  fresh database, so changing the password later means changing it in Postgres or starting over.
- **Postgres 18 moved its data directory.** Older images used `/var/lib/postgresql/data`; 18 keeps
  a directory per major version under `/var/lib/postgresql`, so an upgrade can run next to the old
  data. Mounting the old path with 18 makes the container refuse to start.
- **The healthcheck** asks `pg_isready` until the server takes connections. `up -d --wait`
  returns only when it passes, so `just migrate-platform` right after doesn't hit a database
  still starting.

## `.env` and `.env.example`

`.env` holds the password and is gitignored (since 0.1). `.env.example` is committed with the
same names and no values, so a new checkout knows what to fill in. The justfile reads `.env` with
`-include .env` (the `-` makes it optional, so `just test` still works without one) and `export`
hands every variable to the recipes. That is how goose gets `DATABASE_URL`.

## Migrations with goose

A migration is a SQL file with a version number. goose records the versions it applied in a
table, `goose_db_version`, and `up` applies the rest in order.

```sql
-- +goose Up
CREATE SCHEMA platform;
...

-- +goose Down
DROP TABLE platform.tenants;
...
```

- **Up** moves the database forward; **Down** undoes exactly that. `just migrate-check` runs up,
  `reset` (every Down, newest first) and up again, so a Down that doesn't work is found now and not
  during an emergency rollback.
- goose runs each file in a transaction, so a failing migration leaves nothing half done. Postgres
  can do that because its DDL (`CREATE TABLE` and the like) is transactional; many databases' isn't.
- **A migration that has run is never edited.** Databases that already applied version 1 won't
  run it again, so an edit would make them differ from new ones. Changes go in a new file.
- The Down drops each object by name, not with `DROP SCHEMA ... CASCADE`, which would silently
  take along anything a later migration put in the schema.

## Three kinds of schema

A Postgres **schema** is a namespace inside a database: `platform.tenants` and
`tenant_7.spaces` are tables in two schemas. Unqualified names are looked up along the
`search_path`.

| Schema | Holds | Created by |
| --- | --- | --- |
| `platform` | Data about operators: `tenants`; later support users and the audit log | This migration |
| `shared` | Extensions every tenant needs: `btree_gist` | This migration |
| `tenant_<id>` | One operator's own data: spaces, members, bookings | Provisioning, 2.2 |
| `public` | Only goose's version table | Postgres |

A tenant transaction will set its `search_path` to `tenant_<id>, shared` (2.4). Neither
`platform` nor `public` is on it, so tenant queries can't reach platform tables by an unqualified
name. That is a convenience, not a lock: database roles (5.1) are the lock.

`btree_gist` lives in `shared` because an extension's functions and operators go in one schema,
and every tenant's exclusion constraint has to find them. It lets one GiST index compare
`space_id` with `=` and a time range with `&&` (overlaps), which 2.3 needs.

## The database's own rules

```sql
slug text NOT NULL
     CONSTRAINT tenants_slug_key UNIQUE
     CONSTRAINT tenants_slug_format CHECK (
         slug ~ '^[a-z0-9]+(-[a-z0-9]+)*$'
         AND length(slug) BETWEEN 3 AND 40
     ),
```

- **Check constraints** are rules Postgres enforces on every insert and update, whoever runs it:
  the app, a migration, someone in `psql`. The Go code will check the same things to give good
  error messages, but the database is what makes them always true.
- **Named constraints** (`CONSTRAINT tenants_slug_format`) show up in errors under a name we
  chose. Go code will match on that name, so it must not be whatever Postgres would generate.
- **`status` is text with a check**, not a Postgres `ENUM` type. Adding a value to a check is a
  normal migration; changing an enum type has more restrictions. It matches the string types in Go
  (`SpaceKind`).
- **The slug format** is lowercase letters and digits in groups joined by single hyphens, because
  it goes in URLs. The schema name is built from `id`, never from the slug, so a slug never reaches
  SQL as an identifier.

## Identity columns

```sql
id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY
```

This is the SQL-standard replacement for `serial`. `ALWAYS` means the caller can't choose an id,
so the last insert in the script is refused. `bigint` matches the `int64` IDs in Go.

An identity takes its numbers from a **sequence**, and a sequence is not transactional: a number
handed out is never handed back. In the script every refused insert still used one, so the next
good row would get id 7, not 2. IDs have gaps; they are unique, not counted.

## `ON_ERROR_ROLLBACK`

Inside a transaction, one error makes Postgres refuse every statement after it until `ROLLBACK`.
The script wants to show several refusals in a row, so it turns on psql's
`\set ON_ERROR_ROLLBACK on`: psql puts a savepoint before each statement and rolls back to it when
the statement fails. The transaction carries on, and the final `ROLLBACK` undoes the good insert.
