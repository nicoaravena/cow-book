# 1.8 In-memory store

Step 1.8 adds `internal/memstore`, a store that keeps spaces, members and bookings in maps, and
tests that start many goroutines at once against the real `BookingService` and `MemberService`.
Until now the services only ran against a fake that did whatever the test told it to. Now a store
really has to decide who wins.

## Why the store decides the winner

Booking is read, check, write: `BookingService.Book` builds the booking with `NewBooking`, then
calls `CreateBooking`. Two requests for the same slot can both pass `NewBooking`, because neither
has stored anything yet. Only the store sees every booking, so only the store can refuse the second
one. The same goes for cancel, approve and delete: the domain rule runs on a copy the service read
earlier, and the store's save is where a stale copy gets caught.

In Postgres the exclusion constraint and row updates decide (M2). In memory, a mutex does.

## Goroutines

A goroutine is a function running concurrently with the rest of the program, started with `go`.
They are cheap: thousands are normal. The test helper starts one per racer:

```go
func race(n int, call func(i int) error) []error {
	errs := make([]error, n)
	start := make(chan struct{})
	var wg sync.WaitGroup
	for i := range n {
		wg.Go(func() {
			<-start
			errs[i] = call(i)
		})
	}
	close(start) // a closed channel releases every receiver at once
	wg.Wait()
	return errs
}
```

- **Start barrier.** Each goroutine blocks on `<-start`. Closing a channel wakes every receiver,
  so they all begin together instead of one by one as the loop creates them. Without it, the first
  goroutine could finish before the last one starts, and the race would hardly be a race.
- **`sync.WaitGroup`** counts running goroutines. `wg.Go(f)` (Go 1.25) adds one, runs `f` in a new
  goroutine and marks it done when `f` returns. It replaces the older
  `wg.Add(1); go func() { defer wg.Done(); ... }()`. `wg.Wait()` blocks until the count is zero.
- **No shared writes.** Each goroutine writes only `errs[i]`, its own element, so no two touch the
  same memory. `wg.Wait()` also guarantees that their writes are visible once it returns, so the
  test reads `errs` without a lock.
- **Loop variables.** Since Go 1.22 each iteration has its own `i`, so the closure captures the
  right value. Older code needed `i := i` or passing `i` as an argument.

## `sync.Mutex`

A map is not safe for concurrent use: a write at the same time as any other access is a data race,
and the runtime may crash with `concurrent map writes`. `Store` guards its maps with one mutex:

```go
func (s *Store) CreateBooking(ctx context.Context, b cowbook.Booking) (cowbook.Booking, error) {
	if err := ctx.Err(); err != nil {
		return cowbook.Booking{}, err
	}
	s.mu.Lock()
	defer s.mu.Unlock()

	for _, other := range s.bookings {
		if other.SpaceID() == b.SpaceID() && !other.Cancelled() && overlaps(b, other) {
			return cowbook.Booking{}, cowbook.ErrSlotTaken
		}
	}
	...
}
```

- `Lock` waits until no one else holds the mutex. `defer s.mu.Unlock()` releases it on every
  return path, early returns included.
- The lock covers the whole check and the write. Locking only the write would still let two calls
  both see the slot free, then both store. That is a logic race, and `-race` would not catch it:
  every memory access would be locked.
- The zero `sync.Mutex` is ready to use. A struct holding one must not be copied after use, since
  the copy carries the lock state; `go vet` reports such copies. That is one reason `New` returns
  `*Store`.
- One mutex for everything is simple and plenty here. A real store would lock less (per space,
  or in the database).

## The race detector

`go test -race` builds the program with instrumentation that watches every memory access and
reports two goroutines touching the same memory, at least one of them writing, with nothing
ordering them. `make test` now runs with `-race`.

It only sees races that happen during the run, so the tests must actually make goroutines collide;
the start barrier helps. It finds data races, not logic races: the "lock only the write" mistake
above passes `-race` and is caught by the test's counts instead (exactly one success, the rest
`ErrSlotTaken`). It needs cgo and makes tests slower and hungrier, which is fine at this size.

To see it work, delete the two lock lines in `CreateBooking` and run
`go test -race -run TestRaceForOneSlot ./internal/memstore/`: it prints `WARNING: DATA RACE` with
both goroutines' stacks.

## Values, copies and accessors

The maps hold `cowbook.Booking` and `cowbook.Member` values, not pointers. Returning one hands the
caller a copy, so a caller changing it can't change the store behind the lock. That works because
neither type holds a slice or map; `Space` does (its opening hours), but nothing writes to them
after `NewSpace`.

`memstore` is a separate package, so it can't read unexported fields. Step 1.8 adds read-only
accessors: `SpaceID`, `MemberID`, `Start`, `End`, `Cancelled` and `Approved` on `Booking`, and
`Deleted` on `Member`. They read but can't change, so the domain's rules stay the only way to
change state.

## Compile-time interface checks

```go
var (
	_ cowbook.BookingStore = (*Store)(nil)
	_ cowbook.SpaceStore   = (*Store)(nil)
	_ cowbook.MemberStore  = (*Store)(nil)
)
```

Go interfaces are implicit, so nothing says `Store` means to implement them. These lines assign a
nil `*Store` to a variable of each interface type and throw it away. If a method is missing or has
the wrong signature, the build fails here, with a clear message, instead of at some caller.

## `internal/`

A package under `internal/` can be imported only by code rooted at the parent of `internal`, here
this module. It marks `memstore` (and later `postgres`, `httpapi`, `web`) as parts of this program,
not a library for others.

## What the tests cover

- `memstore_test.go`: the store's contract, one call at a time: IDs, overlap edges (a booking
  ending at 10:00 and one starting at 10:00 don't overlap), a cancelled booking frees its slot, a
  pending one holds it, each loser error, not found, a done context.
- `race_test.go`: 50 goroutines at once through the services: one slot, one winner; a pending
  booking's slot, no winner; one approval wins; approve racing cancel always ends cancelled; one
  deletion wins and cancels every booking.

## Known gaps

- No lazy expiry: a lapsed pending booking keeps its slot here. Postgres gets it in 2.5.
- A booking can still be created for a member deleted at the same moment. 2.6 closes it.
- Saves replace the whole booking, so a cancel that read the booking before an approval was saved
  drops the approval time. Postgres will update only the changed columns.
