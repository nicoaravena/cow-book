# 2.2 Tenant schemas

Step 2.2 gives each operator a schema of its own. The **tenant migration** creates the tables
every operator gets (locations, spaces with their opening windows, members). The
**provisioner** in `internal/postgres` adds a tenant: it inserts the row in `platform.tenants`,
creates `tenant_<id>`, runs the tenant migration in it, and marks the tenant active. If any step
fails, it removes the schema and the row.

`cowbook create-tenant` reaches it from the binary. It was planned for 3.2, but without it there
was nothing to look at.

```sh
make db-up migrate-platform            # as in 2.1
make test-integration                  # the provisioner's tests, against the compose database
make create-tenant SLUG=north-hub NAME="North Hub"
```

```
created tenant 23 (north-hub) in schema tenant_23
```

Your number will differ: the integration tests create and remove tenants, and every id they used
is gone for good ([2.1](2.1-postgres-and-migrations.md#identity-columns)). Use the schema name it
printed:

```sh
docker compose exec -T db psql -U cowbook -d cowbook -v tenant=tenant_23 < examples/2.2-tenant.sql
```

The script adds a location, a space with two Monday windows and a member, then tries eight bad
rows, each refused by a named constraint:

```
ERROR:  new row for relation "spaces" violates check constraint "spaces_kind_valid"
ERROR:  new row for relation "spaces" violates check constraint "spaces_capacity_positive"
ERROR:  new row for relation "spaces" violates check constraint "spaces_max_booking_length_valid"
ERROR:  insert or update on table "spaces" violates foreign key constraint "spaces_location_id_fkey"
ERROR:  new row for relation "opening_windows" violates check constraint "opening_windows_weekday_valid"
ERROR:  new row for relation "opening_windows" violates check constraint "opening_windows_opens_before_closes"
ERROR:  new row for relation "members" violates check constraint "members_email_normalized"
ERROR:  duplicate key value violates unique constraint "members_email_key"
```

Then it deletes Ana and registers her email again, which is allowed, and lists the schema's
tables, `goose_db_version` among them.

Errors from `create-tenant` are Postgres's own for now:

```
cowbook: insert tenant: ERROR: duplicate key value violates unique constraint "tenants_slug_key" (SQLSTATE 23505)
```

The tables and targets are in the [Database reference](../reference/database.md).

## Embedding files with `embed`

The migrations are SQL files, but the binary has to provision tenants wherever it runs, without
the repository next to it. `embed` compiles files into the binary:

```go
//go:embed platform/*.sql tenant/*.sql
var files embed.FS
```

- `//go:embed` is a directive, not a comment: no space after `//`. It must sit right above a
  package-level variable of type `embed.FS`, `string` or `[]byte`.
- Patterns are relative to the source file's directory and can't use `..`. That is why
  `migrations/embed.go` lives next to the SQL, as package `migrations`, and not in
  `internal/postgres`.
- `embed.FS` implements `fs.FS`, the standard read-only file system interface. goose takes an
  `fs.FS`, so it doesn't care whether files come from disk, the binary or a test.

goose looks for migrations at the root of the `fs.FS` it gets. `fs.Sub(files, "tenant")` returns
the subtree with the `tenant/` prefix removed. It can only fail for a malformed path, and `"tenant"`
is a constant, so `sub` panics rather than return an error nobody could handle.

## database/sql and pgx

Go has two ways to talk to Postgres here:

| | `database/sql` | pgx |
| --- | --- | --- |
| What | Standard library interface, any database through a driver | Postgres-only driver with its own API |
| Types | Generic: `sql.NullTime`, scanning into `any` | Postgres types: ranges, `interval`, arrays, `pgconn.PgError` |
| Pool | `*sql.DB` | `*pgxpool.Pool` |

The app uses pgx: it only ever talks to Postgres, and 2.5 needs Postgres errors and ranges. goose
works on any database, so it takes a `*sql.DB`. pgx's `stdlib` package bridges the two:
`stdlib.OpenDB(config)` returns a `*sql.DB` that uses pgx underneath. The provisioner opens one per
migration run and closes it after.

## Building SQL names safely: `pgx.Identifier`

Values go into SQL as parameters (`$1`), never pasted into the string. But a schema name is an
identifier, not a value, and Postgres doesn't accept parameters there: `CREATE SCHEMA $1` is a
syntax error. So the name has to be part of the SQL text.

```go
schema := pgx.Identifier{SchemaName(id)}.Sanitize()   // "tenant_23", with the quotes
p.pool.Exec(ctx, "CREATE SCHEMA "+schema)
```

`Sanitize` puts the name in double quotes and doubles any quote inside it, so whatever the
string holds, it stays one name. The second protection is where the name comes from:
`SchemaName` builds it from the numeric id only. A slug is user input; an `int64` formatted with
`strconv.FormatInt` can only be digits.

`pgx.Identifier{"tenant_23", "members"}` sanitizes to `"tenant_23"."members"`, a qualified name.
The tests use that form.

## One goose table per schema

Each tenant schema must record its own migration version, or 5.5 couldn't tell which tenants a new
migration has reached. goose has no schema option. It creates `goose_db_version` unqualified, and
when it checks whether the table already exists, it looks in `current_schema()`.

`current_schema()` is the first schema on the `search_path` **that exists**. So the provisioner
connects with:

```go
cfg.RuntimeParams["search_path"] = pgx.Identifier{SchemaName(id)}.Sanitize() + ", shared"
```

`RuntimeParams` are sent when the connection starts, so every connection goose opens has that path.
goose's table and every table in the migration land in `tenant_<id>`. `shared` is on the path so
the migrations in 2.3 find `btree_gist`.

The catch is "that exists". If the schema were missing, Postgres would skip it silently,
`current_schema()` would be `shared`, and goose would write the tenant's tables there. That is why
`provision` creates the schema before it migrates, and why `TestCreateTenant` checks that
`goose_db_version` is in the tenant's schema.

## Cleaning up after a failure

```go
if err := p.provision(ctx, id); err != nil {
	cleanupErr := p.remove(context.WithoutCancel(ctx), id)
	return 0, errors.Join(err, cleanupErr)
}
```

- **Undoing by hand.** The steps can't share one transaction: goose runs on its own connection
  and opens its own transactions. So a failure after the insert is undone step by step:
  `DROP SCHEMA ... CASCADE` removes the schema and everything in it, then the row is deleted.
  Here `CASCADE` is right, unlike in a Down migration: the schema is brand new and belongs only to
  this tenant.
- **`context.WithoutCancel(ctx)`** returns a context with the same values but which is never
  cancelled. If the caller gave up (a timeout, Ctrl-C), that may be exactly why provisioning
  failed, and cleaning up with the same cancelled `ctx` would fail too.
- **`errors.Join`** returns one error that holds both. It is `nil` if both are `nil`, prints them
  on separate lines, and `errors.Is` and `errors.As` see through it to either one. The caller
  learns why provisioning failed and, if it happens, that cleanup failed too.

What isn't covered: if the process dies between the insert and the cleanup, the row stays at
`provisioning`. Signup (5.3) will have to deal with rows stuck there.

## Integration tests and build tags

```go
//go:build integration

package postgres
```

A `//go:build` line before the package clause includes the file only when its condition holds. Here
it holds when the build is given the tag: `go test -tags integration`. A plain `go test ./...`
doesn't compile the file at all, so `make test` stays fast and needs no database.
`make test-integration` adds the tag.

`make lint` now passes `-tags integration` to `go vet` and `staticcheck`, or they would skip the
tagged file. Editors skip it too unless told the tag; for gopls that is the `buildFlags` setting
with `-tags=integration`.

The tests need `DATABASE_URL`, which the Makefile loads from `.env`. Without it they fail rather
than skip: the tag means you asked for them.

Each test tenant gets a random `test-` slug and is removed in `t.Cleanup`. Cleanup runs after
`t.Context()` is cancelled, so cleanup code uses `context.Background()`.

## Faking a file system with `fstest.MapFS`

To prove cleanup works, a migration has to fail. Breaking the real files isn't an option, but
the provisioner takes any `fs.FS`:

```go
broken := fstest.MapFS{
	"00001_ok.sql":     {Data: []byte("-- +goose Up\nCREATE TABLE ok (id int);\n")},
	"00002_broken.sql": {Data: []byte("-- +goose Up\nCREATE TABLE ok (id int);\n")}, // already exists
}
```

`fstest.MapFS` is an in-memory `fs.FS` built from a map of names to contents. The first migration
succeeds, the second fails, and the test checks that neither the schema nor the row is left. Taking
the migrations as a parameter rather than reading `migrations.Tenant` inside is the same dependency
injection as the clock in 1.5.

## Checking which constraint refused a row

```go
var pgErr *pgconn.PgError
if !errors.As(err, &pgErr) { ... }
if pgErr.ConstraintName != tt.constraint { ... }
```

`errors.As` looks through the wrapping for an error of type `*pgconn.PgError` and, if it finds
one, stores it in `pgErr`. That is Postgres's error with its fields: `Code` (`23514` for a check,
`23505` for unique), `ConstraintName`, `Message`. Testing the constraint name proves the right rule
refused the row, not just that something did. 2.5 uses the same idea to turn `23P01` into
`ErrSlotTaken`.

## The tenant tables

- **Opening hours as rows.** `opening_windows` holds one row per window: `weekday` 0-6 with Sunday
  0, like `time.Weekday`, and minutes since midnight 0-1440, like `ClockTime`. The database checks
  each row on its own; that windows on one day don't overlap or touch stays in `NewWeeklyHours`,
  which already enforces it for every `Space`.
- **`ON DELETE CASCADE`** on `opening_windows.space_id`: a window can't exist without its space, so
  deleting a space deletes its windows. Spaces have no cascade from locations: deleting a location
  that still has spaces is refused, which is safer for things with bookings.
- **`interval`** stores `max_booking_length`, the Postgres counterpart of `time.Duration`.
  pgx converts between them.
- **Timezone as text.** A check constraint must give the same answer forever, so it can't consult
  the list of zones, which changes with Postgres releases. Go checks it with `time.LoadLocation`
  when locations get managed (3.7).
- **Partial unique index.** `UNIQUE (email) WHERE deleted_at IS NULL` only indexes members who
  aren't deleted. A deleted member keeps their row and history, and the email can register again.
  The check `email = lower(btrim(email))` makes sure the index compares emails the way
  `NewMember` normalizes them.
- **`NULL` for "not happened".** `deleted_at` is `NULL` until deletion, where the domain uses a
  zero `time.Time`. The store maps one to the other in 2.4.
- Default `now()` on timestamps is for psql. The app will pass its own clock's time.

## Known gaps

- Errors from `create-tenant` are raw Postgres messages; there's no `Tenant` domain type to
  validate a slug first yet.
- A crash mid-provisioning leaves a row at `provisioning` with or without a schema (5.3).
- Tenants are provisioned as the superuser, and no tenant role exists yet (5.1).
- Integration tests share the compose database you develop with. They only touch `test-`
  tenants and remove them.
- Only new tenants get migrated. Bringing existing tenants up to a new version is 5.5.
