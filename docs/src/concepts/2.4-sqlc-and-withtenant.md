# 2.4 sqlc and `WithTenant`

Step 2.4 lays the plumbing every Postgres store will use:

- **sqlc** turns SQL queries into typed Go functions.
- **`postgres.NewPool`** opens a pool of connections with a deliberate pgx query mode.
- **`postgres.WithTenant`** runs some work in one transaction, in one tenant's schema.

Its tests prove the part a mistake would make dangerous: a connection goes back to the pool with
no tenant left on it.

The roadmap's 2.4 was split here. The space store becomes 2.4b, and `cowbook repl -store=postgres`
waits for 2.7, when spaces, members and bookings all live in Postgres. So the binary barely changes:
`create-tenant` now opens its pool with `NewPool`. The runnable result is the tests:

```sh
make db-up migrate-platform                # as in 2.1
make generate                              # regenerate internal/postgres/tenantdb; no diff expected
make lint                                  # now also fails if the generated code is stale
make test-integration
go test -race -tags integration -run 'WithTenant|QueryMode' -v ./internal/postgres
```

The last command lists each case:

```text
--- PASS: TestWithTenantSeesOnlyItsSchema
--- PASS: TestWithTenantSearchPathDoesNotCarryOver
    --- PASS: TestWithTenantSearchPathDoesNotCarryOver/commit
    --- PASS: TestWithTenantSearchPathDoesNotCarryOver/error_rolls_back
    --- PASS: TestWithTenantSearchPathDoesNotCarryOver/panic_rolls_back
--- PASS: TestQueryModeAcrossSchemaVersions
    --- PASS: TestQueryModeAcrossSchemaVersions/cache_statement
    --- PASS: TestQueryModeAcrossSchemaVersions/describe_exec
```

The reference is in [Database](../reference/database.md#tenant-transactions).

## Generated code with sqlc

Hand-written database code repeats itself. You write the SQL, list the arguments in the right
order, `Scan` each column into the right Go type, and keep all of that in step with the tables.
sqlc does it the other way round: you write the SQL, and it writes the Go. It reads
`sqlc.yaml`, which points at two things:

- the schema: `migrations/tenant/`, the goose files. sqlc understands goose's `-- +goose Up` and
  `Down` markers and reads only the Up parts;
- the queries: `internal/postgres/queries/*.sql`, each one named with a comment:

```sql
-- name: GetLocation :one
-- GetLocation returns pgx.ErrNoRows if the tenant has no such location.
SELECT id, name, timezone FROM locations WHERE id = $1;
```

From that it writes `internal/postgres/tenantdb/`, a package with one method per query:

```go
func (q *Queries) GetLocation(ctx context.Context, id int64) (GetLocationRow, error)
```

`:one` means one row back, so the method returns a struct, or `pgx.ErrNoRows` when there's none.
`:many` would return a slice and `:exec` only an error. The column types come from the
migrations: `id` is `bigint`, so it is `int64`. A query naming a missing column fails at
`make generate`, not when a user first hits it. Comments under the `-- name:` line become the
method's doc comment.

Every generated file starts with `// Code generated by sqlc. DO NOT EDIT.` That line is a Go
convention, not decoration. Tools such as `staticcheck` and `gopls` recognize it and treat the
file as machine-written. Changes go in the SQL, and `make generate` rewrites the files.

The generated code is **committed**. `go build` then needs neither sqlc nor a C compiler: sqlc
parses SQL with Postgres's own parser, built with cgo, so its first build takes about 30 seconds.
Committing it brings one risk, that the files fall behind the SQL. `make lint` closes that gap
with `go tool sqlc diff`, which exits 1 if generating again would change anything.

## A pool, and why connections get reused

Opening a Postgres connection costs a network round trip, authentication and a new server
process. A pool (`pgxpool.Pool`) keeps a few connections open, lends one to each query or
transaction, and takes it back afterwards. One connection therefore serves many tenants, one after
another.

That reuse is what 2.4 had to make safe. A session setting such as `SET search_path = tenant_1`
stays on the connection. The next borrower, maybe serving tenant 2, would start in tenant 1's
schema. The README's "no operator sees another's data" would then depend on every caller
remembering to reset it.

## Settings that end with the transaction

`WithTenant` sets the path like this:

```go
tx.Exec(ctx, "SELECT set_config('search_path', $1, true)", path)
```

The third argument, `is_local = true`, makes it the same as `SET LOCAL`: the setting lasts until
the transaction ends, by commit or rollback, and then the connection's own value comes back. Nothing
has to undo it.

`set_config` is a function, so the path can be a `$1` parameter. `SET LOCAL search_path = ...` is
a statement and can't take parameters, so the path would have to be pasted into the SQL text. The
value is still built with `pgx.Identifier{...}.Sanitize()`, which quotes the schema name, because
Postgres parses it as a list of names (see 2.2's
[`pgx.Identifier`](2.2-tenant-schemas.md#building-sql-names-safely-pgxidentifier)).

## Closures for transaction scope

```go
func WithTenant(ctx context.Context, pool *pgxpool.Pool, tenantID int64,
	fn func(q *tenantdb.Queries) error) error
```

The caller passes the work as a function, and `WithTenant` owns everything around it: begin, set
the path, call `fn`, then commit or roll back. A store method will read like this:

```go
err := postgres.WithTenant(ctx, pool, tenantID, func(q *tenantdb.Queries) error {
	row, err := q.GetLocation(ctx, id)
	if err != nil {
		return err
	}
	loc = row // loc lives outside the closure
	return nil
})
```

The function literal is a **closure**: it uses `ctx`, `id` and `loc` from the code around it, and
assigning `loc` inside changes the outer variable. That's how results get out, since `fn` itself
only returns an error.

Two things come from the shape. A caller can't forget to commit, roll back, or set the path,
because it never gets the transaction, only `*tenantdb.Queries` bound to it. And the
scope is visible: everything inside the braces is one transaction, in one tenant. 5.1 adds
`SET LOCAL ROLE` in the same place, and no caller changes.

## `defer` and rolling back

```go
tx, err := pool.Begin(ctx)
...
defer tx.Rollback(context.WithoutCancel(ctx))
```

A deferred call runs when the function returns, by any path:

- an early `return` after an error;
- the normal end after `Commit`, where `Rollback` finds the transaction closed and does nothing.
  Its error (`pgx.ErrTxClosed`) is ignored on purpose;
- a **panic** in `fn`. Deferred calls run while a panic unwinds the stack, so the transaction is
  rolled back and the connection goes back to the pool clean. The panic then carries on up.

`context.WithoutCancel(ctx)` keeps `ctx`'s values but drops its cancellation, as in 2.2's cleanup:
if `ctx` was cancelled, that's often why we're rolling back, and the rollback must still reach
Postgres.

The test's `callRecovering` shows the other half of the panic mechanism. `recover()`, called inside
a deferred function, stops a panic, and the deferred function can set a named result:

```go
func callRecovering(f func() error) (panicked bool, err error) {
	defer func() {
		if recover() != nil {
			panicked = true
		}
	}()
	return false, f()
}
```

## Proving nothing carries over

`TestWithTenantSearchPathDoesNotCarryOver` opens a pool of exactly one connection:
`pool_max_conns=1`, a pgxpool setting read from the URL. It records `pg_backend_pid()`, the id of
the server process behind that connection, and the `search_path`. Then it runs `WithTenant` three
ways, as a table of closures: one commits, one returns an error, one panics. After each it checks:

- the pid is unchanged, so this really is the same connection and the test proves what it claims;
- `search_path` is back to the default;
- an unqualified `SELECT 1 FROM locations` fails with `42P01` (`undefined_table`). Outside
  `WithTenant` no tenant table is visible, so a forgotten wrapper fails closed instead of reading
  whichever tenant came last;
- the location `fn` inserted exists after the commit and is gone after the error and the panic.

## Query exec modes and stale plans

pgx can send a query in several ways, its **query exec modes**. The default, `cache_statement`,
prepares each SQL text once per connection and afterwards sends only the statement's name and the
arguments: one round trip, with the types already known.

Prepared statements and schema-per-tenant don't mix well, though. The same text,
`SELECT id, name, timezone FROM locations ...`, means a different table under each tenant's
`search_path`. Postgres notices the path changed and plans the statement again, but the
statement's result columns were fixed when it was prepared. If the other tenant's table differs,
it refuses:

```text
ERROR:  cached plan must not change result type
```

That happens whenever tenants are on different migration versions. While a migration rolls out
across tenants (5.5), they are. `TestQueryModeAcrossSchemaVersions` reproduces it. It changes tenant
b's `locations.name` to `varchar`, then runs `GetLocation` in a and then in b on one connection.
Under `cache_statement` b fails with SQLSTATE `0A000`; under the pool `NewPool` builds, both work.

`NewPool` uses `describe_exec`. It asks Postgres to describe each query, then runs it, with no
cache to go stale. The cost is a second round trip per query, which is small locally. The other
cache-free mode, `exec`, uses one round trip but works out parameter types from the Go values. It
is the option if latency ever matters.

## Build tags, again

The new tests carry `//go:build integration`, like 2.2's
([build tags](2.2-tenant-schemas.md#integration-tests-and-build-tags)), so `make test` stays
database-free. Editors run their analysis without the tag unless told otherwise. gopls reports
"No packages found" on these files, and adding `-tags=integration` to its `buildFlags` setting
fixes that.

## Known gaps

- Only two queries exist so far, `CreateLocation` and `GetLocation`, enough to exercise the
  wrapper. 2.4b adds the space queries.
- `WithTenant` doesn't check that the tenant exists or is active. A missing schema fails closed;
  suspended operators are 5.4.
- sqlc only reads the tenant migrations. Platform queries (`Provisioner`, the slug lookup in 2.7)
  stay hand-written.
- sqlc adds about 30 indirect entries to `go.mod`, like goose did.
