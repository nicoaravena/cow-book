# 1.7 Deleting a member

Step 1.7 adds `MemberService.Delete`: it marks the member deleted and cancels every booking of
theirs that hasn't ended, pending ones and ones in progress included. A deleted member acting as a
member is refused by `Book`, `Cancel` and `Approve`. One store method saves the deletion and the
cancellations together.

## A rule without an actor

`Cancel` checks who asks. When a member is deleted, nobody asks: the system cancels. 1.7 splits the
method:

```go
func (b *Booking) Cancel(actor Actor, space Space, now time.Time) error {
	if space.ID != b.spaceID || !actor.actsFor(b.memberID, space.locationID) {
		return ErrCancelNotAllowed
	}
	return b.cancel(now)
}

// cancel holds Cancel's rules without the actor check, for when the system
// cancels and not a person, as when a member is deleted.
func (b *Booking) cancel(now time.Time) error { ... }
```

The lowercase `cancel` can't be called from outside `cowbook`, so skipping the actor check stays a
decision made inside the domain. A fake "system" actor that may do anything would have been
exported and reusable by mistake.

## Slices of values: changing elements in a loop

```go
func cancelBookings(bs []Booking, now time.Time) []Booking {
	var cancelled []Booking
	for i := range bs {
		if bs[i].cancel(now) == nil {
			cancelled = append(cancelled, bs[i])
		}
	}
	return cancelled
}
```

- `for _, b := range bs` gives a **copy** of each element. `b.cancel(now)` would cancel the copy
  and leave `bs` unchanged, silently.
- `bs[i]` is addressable, so `bs[i].cancel(now)` calls the pointer method on the element itself.
- `append(cancelled, bs[i])` copies the cancelled booking into the result.
- `var cancelled []Booking` is a nil slice. `append` works on nil, so it needs no `make`.

A `[]*Booking` would avoid the index, but then every holder of the slice shares and can change the
same bookings. Values keep each owner's copy its own; 1.8 relies on that.

## A batch saved all or nothing

```go
SaveDeletion(ctx context.Context, m Member, cancelled []Booking) error
```

The member and their cancellations go to the store in one call, so Postgres can use one transaction
(2.6). Two separate saves could leave a deleted member with active bookings if the second failed.
The method lives on `MemberStore`, rather than a fourth interface, at the cost that whatever
implements `MemberStore` for `BookingService` implements it too.

## Refusing a deleted actor first

```go
func (s *BookingService) refuseDeletedMember(ctx context.Context, actor Actor) error {
	if actor.role != roleMember {
		return nil
	}
	m, err := s.members.GetMember(ctx, actor.id)
	...
	if !m.deletedAt.IsZero() {
		return ErrMemberDeleted
	}
	return nil
}
```

`Cancel` and `Approve` call it before anything else. It's about the actor themselves, so it leaks
nothing, and `ErrMemberDeleted` says more than whatever the booking would have said. Staff skip the
lookup, and they can still cancel a deleted member's bookings.

## Known gaps

- Who may delete a member isn't checked yet (3.7, 4.6).
- `Delete` lists bookings, then saves: a booking created between the two stays active. 2.6 closes
  it in one transaction.
