# 2.6 Cancelling and deleting in transactions

Step 2.6 finishes the Postgres booking store and starts the member store:

- **`postgres.BookingStore`** gets `SaveCancellation` and `ListMemberBookingsEndingAfter`, so it
  now implements `cowbook.BookingStore`, checked at compile time. A cancelled booking's slot is
  bookable again at once.
- **`postgres.MemberStore`** has `GetMember` and `SaveDeletion`. `SaveDeletion` marks the member
  deleted and cancels their bookings in one transaction.
- **Deleting and booking at once is safe.** `CreateBooking` locks the member's row before it
  inserts, and `SaveDeletion` locks the same row before it cancels, so one always waits for the
  other. A booking that arrives during a deletion is either refused with `ErrMemberDeleted` or
  cancelled by the deletion; none is left active.
- **`cowbook.RestoreMember`** rebuilds a `Member` from stored values, and `Member` gets
  `CreatedAt`, `UpdatedAt` and `DeletedAt`.

Creating and listing members, and the REPL on Postgres, are 2.7's. So the runnable result is
still the tests, now including `BookingService` and `MemberService` running over the three
Postgres stores:

```sh
just db-up migrate-platform                # as in 2.1
just generate                              # no diff expected
just test-integration
go test -race -tags integration -run 'Member|Cancel|Waits|WhileDeleting' -v ./internal/postgres
go test -race -tags integration -run 'Race|Waits' -count=20 ./internal/postgres
```

## Cancelling: one more guarded `UPDATE`

`SaveCancellation` follows `SaveApproval` from
[2.5](2.5-booking-store.md#checking-and-writing-in-one-statement): the check is in the `WHERE`,
so the check and the write are one statement.

```sql
UPDATE bookings
SET cancelled_at = @cancelled_at, updated_at = @updated_at
WHERE id = @id
  AND cancelled_at IS NULL;
```

Of two racing cancels, the second `UPDATE` waits for the first one's row lock, then re-checks
`cancelled_at IS NULL`, finds it false and changes nothing. With 0 rows changed, the store reads
the row in the same transaction: no row is `ErrBookingNotFound`, any row is
`ErrAlreadyCancelled`. `TestBookingStoreRaceToCancel` races fifty of them and counts one winner.

It writes only the two cancel columns. A cancel that read the booking before an approval was
saved leaves `approved_at` alone, where the in-memory store would put the old copy back whole.
`TestBookingStoreCancelKeepsApproval` checks it. Once `cancelled_at` is set, the exclusion
constraint ignores the row, so the slot is free the moment the transaction commits.

## Transactions spanning several queries

`WithTenant` from [2.4](2.4-sqlc-and-withtenant.md#closures-for-transaction-scope) runs a closure
in one transaction. 2.5's closures ran one or two statements; `SaveDeletion` runs several, with
a loop and an early return:

```go
return WithTenant(ctx, s.pool, s.tenantID, func(q *tenantdb.Queries) error {
	n, err := q.DeleteMember(ctx, ...)         // 1. mark deleted, lock the row
	if err != nil {
		return err
	}
	if n == 0 {
		...                                     // not found or already deleted
		return cowbook.ErrMemberDeleted
	}
	for _, b := range cancelled {               // 2. the bookings the service cancelled
		if _, err := q.CancelBooking(ctx, cancelParams(b)); err != nil {
			return err
		}
	}
	_, err = q.CancelMemberBookingsEndingAfter(ctx, ...) // 3. any it missed
	return err
})
```

Nothing new is needed in Go for this. Every query goes through the same `q`, which is bound to
the one transaction, and any `return err` rolls all of it back: `WithTenant`'s deferred
`Rollback` runs, and `Commit` is never reached. So "all or nothing", the `MemberStore` contract
from [1.7](1.7-deleting-a-member.md#a-batch-saved-all-or-nothing), holds without code of its own.
The memstore got the same promise by holding its mutex for the whole method.

The domain decides what is cancelled: `MemberService.Delete` lists the bookings, runs the
unexported `cancelBookings` on them, and passes the result in. A `CancelBooking` that changes 0
rows is fine here: someone else cancelled that booking meanwhile, and their cancellation stays,
as the contract says.

## Row locks

Every `UPDATE` locks the rows it changes until its transaction ends. A `SELECT` can lock rows too,
with a locking clause at the end. Postgres has four row lock strengths. Each pair below either
lets both holders in at once or makes the second wait:

| Taken by | Mode | Waits for |
| --- | --- | --- |
| A foreign key check | `FOR KEY SHARE` | `FOR UPDATE` only |
| `SELECT ... FOR SHARE` | `FOR SHARE` | `FOR NO KEY UPDATE`, `FOR UPDATE` |
| `UPDATE` of non-key columns | `FOR NO KEY UPDATE` | `FOR SHARE` and stronger |
| `DELETE`, `UPDATE` of a key, `SELECT ... FOR UPDATE` | `FOR UPDATE` | everything |

Many transactions can hold `FOR SHARE` on one row at once: concurrent bookings of one member don't
wait for each other. Each conflicts with `FOR NO KEY UPDATE`, which `DeleteMember`'s `UPDATE`
takes. So:

- `CreateBooking` starts with `LockMember`, `SELECT deleted_at FROM members WHERE id = $1 FOR
  SHARE`, and holds that lock until it commits.
- `SaveDeletion` starts with `DeleteMember`, an `UPDATE ... WHERE id = @id AND deleted_at IS
  NULL`, and holds that lock until it commits.

Whichever reaches the row second waits for the first to commit or roll back.

### What the waiting side sees

Under READ COMMITTED, Postgres's default, a statement that waited for a row lock reads the row
again once it gets it, as committed by the other transaction, and re-checks its `WHERE`
([2.5](2.5-booking-store.md#many-at-once) relied on the same thing). That gives both orders a
safe ending:

- **Deletion first.** `LockMember` waits, then reads `deleted_at` as the deletion committed it:
  set. `CreateBooking` returns `ErrMemberDeleted` without inserting.
- **Booking first.** `DeleteMember` waits, then re-checks `deleted_at IS NULL`, still true, and
  goes on. Its later statements each start with a fresh view of the database, which includes the
  committed booking, so step 3 sees it and cancels it.

### Why the foreign key isn't enough

`bookings.member_id` references `members`, and a foreign key check locks the member row too. But
it takes `FOR KEY SHARE`, the weakest mode: it only stops the row being deleted or its key
changed. `deleted_at` is not a key, so `DeleteMember`'s `UPDATE` doesn't wait for it. Without
`LockMember`, a booking insert would read the member as not deleted, from before the deletion
committed, and go ahead. Hence the roadmap's two options, "lock the member row, or insert only
while the member isn't deleted": an `INSERT ... SELECT ... WHERE deleted_at IS NULL` without a
lock reads the same stale row, so the lock is the one that works.

## Lock, then sweep

`MemberService.Delete` reads, then saves: it lists the bookings, cancels them in Go, then calls
`SaveDeletion`. A booking made between the list and the save isn't in `cancelled`. The member's
row lock doesn't help with that one: the booking committed before the deletion took the lock.

So `SaveDeletion` ends with one more statement, after the lock:

```sql
UPDATE bookings
SET cancelled_at = @now, updated_at = @now
WHERE member_id = @member_id
  AND cancelled_at IS NULL
  AND ends_at > @now;
```

`@now` is `m.DeletedAt()`, the clock the service gave `Member.Delete`, so a straggler gets the
same `cancelled_at` as the bookings the service cancelled. The condition is the listing's, and
`Booking.cancel`'s: not cancelled, and not ended. With the member row locked, no new booking can
appear after this statement, so it is the last one that could be missed.

The rule "which bookings a deletion cancels" now lives in SQL as well as in Go. That cost was
chosen over the alternatives:

- **Ignoring `cancelled` and only sweeping:** fewer round trips, but one implementation would take
  a parameter it never reads.
- **A unit-of-work interface:** the store locks, lists and calls a domain function in its
  transaction. That keeps the rule only in Go, but it changes `MemberStore`, the memstore, the
  service and their tests for one race.

`TestMemberStoreSaveDeletionCancelsStragglers` plays the gap out step by step: list, book, then
save with the stale list.

## Lock order and deadlocks

Two transactions deadlock when each waits for a lock the other holds. Postgres notices after a
second and fails one of them with `40P01`. So the order in which each transaction takes its locks
matters:

- `CreateBooking`: the member row, then the space's lapsed bookings (lazy expiry), then the new
  row.
- `SaveDeletion`: the member row, then that member's bookings.

Both take the member row first, so two of them for one member queue on it instead of crossing.
A booking for member A whose lazy expiry touches a lapsed booking of member B, while B is being
deleted, waits for B's deletion. B's deletion waits for nothing A's booking holds, so there is no
cycle. The 2.5 risk about the exclusion constraint itself still stands: two conflicting inserts
could in principle deadlock, and none has been seen.

## Testing an order of events

A race test starts many goroutines and checks what holds after any order. It can't say which
order ran, so it may never hit the one that matters. `TestBookingWaitsForADeletionInFlight` and
`TestDeletionWaitsForABookingInFlight` fix the order instead:

1. The test opens its own transaction, `holdTx`, and does the first half: marks the member
   deleted, or locks the member and inserts a booking. It doesn't commit.
2. A goroutine calls the store, which must now wait on that row.
3. `waitUntilBlockedBy` polls Postgres until it confirms the wait:

   ```sql
   SELECT EXISTS (SELECT 1 FROM pg_stat_activity WHERE $1::int = ANY (pg_blocking_pids(pid)))
   ```

   `pg_blocking_pids(pid)` lists the processes a server process is waiting for, and `$1` is the
   held transaction's process, from `tx.Conn().PgConn().PID()`.
4. The test commits and reads the goroutine's result from a channel.

The goroutine sends its error on a channel with room for one value, so it never blocks, and only
the test's own goroutine calls `t.Fatal`. Step 3 has a five-second deadline: if nothing ever
waits, the test fails rather than hanging.

### Proving the tests can fail

A test that passes proves something only if it would fail without the code it guards. Both guards
were taken out in turn while writing this step:

- **`FOR SHARE` removed:** `TestBookingWaitsForADeletionInFlight` fails with "nothing waited".
- **The sweep removed:** the straggler test, `TestDeletionWaitsForABookingInFlight` and
  `TestRaceToBookWhileDeleting` fail with active bookings left behind.

`TestRaceToBookWhileDeleting` then checks the same thing under real contention, through
`BookingService` and `MemberService` over the Postgres stores: sixteen bookings for one member
race one deletion, and every booking ends refused or cancelled.

## Rebuilding a member

`RestoreMember` goes through `NewMember`, as `RestoreSpace` goes through `NewSpace`
([2.4b](2.4b-space-store.md#rebuilding-through-the-constructor)). A member has no rule that a
stored row could outgrow, unlike a booking's "no start in the past". `MemberRecord` embeds
`MemberParams`, the shape `SpaceRecord` and `BookingRecord` already have.

`TestMemberServiceDeleteOverPostgres` runs the whole deletion against real tables at 12:00. The
member's in-progress booking and their lapsed pending booking are cancelled at 12:00. Their ended
booking and another member's booking stay as they are.

## Known gaps

- `internal/memstore` doesn't refuse a booking for a member deleted at the same moment, and its
  `SaveDeletion` cancels only the bookings it is given. The interface doesn't promise either, so
  only the Postgres store does them.
- `MemberStore` can't create or list members until 2.7, so the integration tests still insert
  members with plain SQL.
- `CreateBooking` now takes one more statement and a row lock per booking. Bookings of one member
  share the lock, so they don't wait for each other.
