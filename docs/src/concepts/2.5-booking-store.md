# 2.5 Booking store

Step 2.5 puts bookings in Postgres:

- **`postgres.BookingStore`** creates, gets and approves one tenant's bookings, each call in one
  `WithTenant` transaction. An overlap refused by the 2.3 exclusion constraint becomes
  `cowbook.ErrSlotTaken`.
- **Lazy expiry:** a pending booking whose approval deadline has passed stops holding its slot.
  `CreateBooking` cancels the ones in its way, in its own transaction, before it inserts.
- **`SaveApproval`** checks and writes in one `UPDATE`, deadline included, so of two racing
  approvals only one gets through.
- **`cowbook.RestoreBooking`** rebuilds a `Booking` from stored values, and `Booking` gets the
  accessors a store needs to write one: `BookedBy`, `ApprovedAt`, `CancelledAt`, `CreatedAt`,
  `UpdatedAt`.

`SaveCancellation` and `ListMemberBookingsEndingAfter` are 2.6's, with member deletion. The REPL
still runs on the in-memory store until 2.7, so the runnable result is the tests:

```sh
make db-up migrate-platform                # as in 2.1
make generate                              # no diff expected
make test-integration
go test -race -tags integration -run BookingStore -v ./internal/postgres
go test -race -tags integration -run BookingStoreRace -count=20 ./internal/postgres
```

The fourth command lists each case:

```text
--- PASS: TestBookingStoreCreateAndGet
--- PASS: TestBookingStoreRefusesOverlaps            (8 subtests)
--- PASS: TestBookingStorePendingBookingHoldsItsSlot
--- PASS: TestBookingStoreSaveApprovalLosers         (2 subtests)
--- PASS: TestBookingStoreSaveApprovalAfterDeadline
--- PASS: TestBookingStoreNotFound                   (2 subtests)
--- PASS: TestBookingStoreUnknownSpaceOrMember
--- PASS: TestBookingStoreOtherTenant
--- PASS: TestBookingStoreLazyExpiry                 (7 subtests)
--- PASS: TestBookingStoreRaceForOneSlot

```

The last one runs the three races 20 times each, since a race that passes once can still fail on
another run. The reference is in [Stores](../reference/stores.md#internalpostgres) and
[Booking](../reference/booking.md#restorebookingr-bookingrecord-booking-error).

## One error, several meanings: `errors.As` and a `switch`

2.4b mapped one Postgres error to one domain error. `CreateBooking` has three to tell apart, so
`errors.As` runs once and a `switch` reads the code and the constraint name:

```go
var pgErr *pgconn.PgError
if errors.As(err, &pgErr) {
	switch {
	case pgErr.Code == "23P01" && pgErr.ConstraintName == "bookings_no_overlap":
		return cowbook.Booking{}, cowbook.ErrSlotTaken
	case pgErr.Code == "23503" && pgErr.ConstraintName == "bookings_space_id_fkey":
		return cowbook.Booking{}, cowbook.ErrSpaceNotFound
	case pgErr.Code == "23503" && pgErr.ConstraintName == "bookings_member_id_fkey":
		return cowbook.Booking{}, cowbook.ErrMemberNotFound
	}
}
```

`errors.As` takes a **pointer to** the variable it should fill, `&pgErr`, because it has to set it.
`pgErr` is itself a pointer, `*pgconn.PgError`, since that is the type pgx returns, so the
argument is a pointer to a pointer. Any other error, a lost connection for one, falls through the
`switch` and comes back as it is.

Checking the constraint name as well as the code matters: `23503` alone says "some foreign key",
and a constraint added later with the same code shouldn't be mistaken for one of these. The two
foreign keys only fire if the space or member was deleted between the service reading it and the
insert. `BookingService.Book` reads both first.

## Lazy expiry

The constraint ignores cancelled rows, `WHERE (cancelled_at IS NULL)`. It can't also ignore
lapsed ones, `WHERE approval_deadline > now()`: a constraint's condition must give the same
answer every time it is asked about a row, and `now()` doesn't (see
[2.3](2.3-bookings.md#a-partial-constraint-and-why-now-cant-be-in-it)). So a lapsed booking stays
in the index, holding its slot, until something cancels it. `CreateBooking` does, just before its
insert:

```sql
UPDATE bookings
SET cancelled_at = @now, updated_at = @now
WHERE space_id = @space_id
  AND cancelled_at IS NULL
  AND approved_at IS NULL
  AND approval_deadline <= @now
  AND tstzrange(starts_at, ends_at) && tstzrange(@starts_at::timestamptz, @ends_at::timestamptz);
```

Only the bookings in the new one's way are touched; a lapsed booking elsewhere waits until
someone needs its slot. `<=` matches `Booking.State`, where a booking expires at its deadline,
the same moment `Approve` starts refusing it. `space_id =`, `cancelled_at IS NULL` and the range
`&&` are the exclusion constraint's own terms, so Postgres can find the rows with the
constraint's gist index.

The `::timestamptz` casts tell sqlc, and Postgres, what type `@starts_at` is. Inside
`tstzrange(...)` it can't tell on its own.

### Whose clock

`@now` is `b.CreatedAt()`. `NewBooking` set that from the clock the service was given, so the
store needs no clock of its own and the `BookingStore` interface stays as it was. The database's
`now()` would be a second clock: the tests couldn't choose it, and it could disagree with the
`now` that `NewBooking` and `State` used.

### One transaction

The `UPDATE` and the `INSERT` run in one `WithTenant`. If the insert is refused, the expiry rolls
back too. Nothing is lost: the booking is still lapsed, and the next attempt cancels it again.
`TestBookingStoreLazyExpiry/insert_refused` proves it: the new booking overlaps a lapsed one and
a confirmed one, gets `ErrSlotTaken`, and the lapsed one is still not cancelled.

### Many at once

Fifty requests may arrive for one lapsed slot. Postgres runs each transaction at **READ
COMMITTED**, its default. The first `UPDATE` to reach the lapsed row locks it. The others wait for
that lock. When the first commits, each waiting `UPDATE` reads the row again and re-checks its
`WHERE`: `cancelled_at` is now set, so it skips the row and changes nothing. Then every insert
meets the exclusion constraint, and exactly one wins. `TestBookingStoreRaceForALapsedSlot` checks
the counts: one success, 49 `ErrSlotTaken`.

## Checking and writing in one statement

`Booking.Approve` checks in Go, on a copy the service read earlier. Two requests can both pass it,
the read, check, write race from [1.5](1.5-services-and-stores.md#read-check-write). The memstore
held a mutex for its check and write. Postgres puts the check in the `UPDATE`'s `WHERE`:

```sql
UPDATE bookings
SET approved_at = @approved_at, updated_at = @updated_at
WHERE id = @id
  AND cancelled_at IS NULL
  AND approved_at IS NULL
  AND approval_deadline > @approved_at;
```

Under READ COMMITTED, of two such `UPDATE`s on one row, the second waits for the first and then
re-checks: `approved_at` is set, so it changes nothing. A member's own booking has a `NULL`
deadline, and a comparison with `NULL` is never true, so it never matches either. The deadline is
checked here as well as in `Approve`: a lazy expiry and an approval can't both win.

sqlc's `:execrows` makes the query return how many rows changed, from pgx's `RowsAffected()`.
`1` means approved. `0` means refused, but not why, so `SaveApproval` reads the row in the same
transaction and `approvalRefusal` names the reason in `Approve`'s order:

```go
switch {
case row.CancelledAt.Valid:
	return cowbook.ErrAlreadyCancelled
case row.ApprovedAt.Valid || !row.ApprovalDeadline.Valid:
	return cowbook.ErrNotPending
case !approvedAt.Before(row.ApprovalDeadline.Time):
	return cowbook.ErrApprovalExpired
}
```

It is a plain function of a row and a time, so `TestApprovalRefusal` tests it without a
database. If none of the cases fits, the booking is still pending and the `UPDATE` should have
matched it: that is a bug, so it returns an error that is none of the refusals.

`SaveApproval` writes two columns, not the whole booking. The memstore replaces the whole booking,
so a cancel that read it before an approval was saved can drop the approval time
([Stores](../reference/stores.md#internalmemstore)). Postgres doesn't copy that shortcut.

## Rebuilding without the constructor

[2.4b](2.4b-space-store.md#rebuilding-through-the-constructor) sent a stored space through
`NewSpace`. `NewBooking` can't do that job: it needs the actor who booked and the space, and it
refuses a start in the past, which most stored bookings will have one day. So `RestoreBooking`
checks only the rules that hold for a booking forever (a member, a space, an attendee, an end
after the start) and sets the fields. `BookingRecord` embeds `BookingParams` the way
`SpaceRecord` embeds `SpaceParams`.

`NULL` columns arrive as `pgtype` values with `Valid` false, whose `Time` is the zero time. That
is already the domain's "not set", so `bookingFromRow` passes `.Time` straight on. Writing, two
small helpers go the other way:

```go
func timestamptz(t time.Time) pgtype.Timestamptz {
	return pgtype.Timestamptz{Time: t, Valid: !t.IsZero()}
}

func nullableID(id int64) pgtype.Int8 {
	return pgtype.Int8{Int64: id, Valid: id != 0}
}
```

## Subtests and shared test helpers

The tests are memstore's, ported, with the same names after a `BookingStore` prefix. They can't
be shared as code: a `_test.go` file belongs to its package's tests and no other package can
import it. So each package keeps its own helpers, and within `internal/postgres` the helpers are
shared by every test file with the `integration` tag.

`newBookingFixture(t, n)` builds what a booking needs, a tenant with a location, two spaces and
`n` members, and returns a struct whose methods keep each test short:

```go
f := newBookingFixture(t, 2)
pending := f.create(t, f.newBooking(t, cowbook.AdminActor(9), 0, f.members[0], 10, 12, bookingNow))
```

Methods on a test-only type are an ordinary way to group helpers that share state. Each calls
`t.Helper()`, so a failure points at the test's line, not the helper's. The members are inserted
with plain SQL, since there is no member store until 2.6. `generate_series(1, $1)` gives one row
per number, so one statement adds all fifty racers, and `pgx.CollectRows(rows,
pgx.RowTo[int64])` reads their ids into a slice.

`TestBookingStoreLazyExpiry` is one table of subtests. Each case may run a `before` function on
the fixture (approve the staff booking, or add a confirmed one) and then says what the new
booking's error should be and whether the staff booking ends up cancelled. Each subtest builds
its own tenant, so a failure in one can't leak into the next, and `go test -run
'LazyExpiry/at_the_deadline'` runs a single case; spaces in a subtest's name become `_`.

The race tests copy `race`, `count` and `checkCounts` from memstore's `race_test.go`. Fifty
goroutines share a pool of fewer connections, so some wait for one, but those holding one run
their transactions in Postgres at the same moment.

### Comparing bookings

Memstore's tests compare bookings with `==`. That fails here: pgx stores whole microseconds and
hands times back in `time.Local`, and a `time.Time` holds its location, so two values for the
same instant aren't `==`. `checkSameBooking` compares the IDs and counts with `!=` and each time
with `Equal`, after cutting the expected time to the microsecond, as
[2.4b](2.4b-space-store.md#timestamps-lose-their-nanoseconds) found.
`TestBookingStoreCreateAndGet` uses a clock with nanoseconds on purpose.

## Known gaps

- `postgres.BookingStore` doesn't implement `cowbook.BookingStore` yet: `SaveCancellation` and
  `ListMemberBookingsEndingAfter` arrive in 2.6, and with them `var _ cowbook.BookingStore =
  (*BookingStore)(nil)`.
- A lapsed booking stays uncancelled in the table until a new booking needs its slot. Anything
  that shows free slots or lists bookings (3.4, 3.6) must use `State(now)`.
- The in-memory store has no lazy expiry, by choice. A lapsed booking there keeps its slot.
- `CreateBooking` doesn't yet refuse a member deleted at the same moment. That is 2.6.
